Project documentation

Telegram → Claude Agent → Draft Pull Request

telegram-agent-bridge lets an authorized Telegram chat request a code change in plain English and get back a draft GitHub pull request. A Claude Agent SDK session does the coding; every git and GitHub action around it — cloning, branching, committing, pushing, opening the PR — is deterministic code, never something the model runs itself. Nothing merges automatically.

/task in Telegram→SQLite job queue→clone + branch→Claude Agent SDK→commit + push→draft PR→Telegram reply

Architecture

Two independent long-running processes share one SQLite database — no message broker, no external queue.

flowchart LR
    subgraph P1["Process 1 — bot + API  (src/index.ts)"]
      TG["Telegraf bot\nlong polling"]
      API["Fastify API\nGET /health\nGET /jobs/:id"]
    end
    subgraph P2["Process 2 — worker  (src/worker.ts)"]
      POLL["Poll loop\nevery JOB_POLL_INTERVAL_MS"]
      PIPE["processJob()\nclone → agent → commit → PR"]
    end
    DB[("SQLite\njobs table\nWAL mode")]
    TELE(["Telegram"])
    GH(["GitHub API"])
    AI(["Anthropic API"])

    TELE <--> TG
    TG -- "insert job" --> DB
    API -- "read job" --> DB
    DB -- "claim pending job" --> POLL
    POLL --> PIPE
    PIPE <--> GH
    PIPE <--> AI
    PIPE -- "update status" --> DB
    PIPE -- "reply" --> TELE

Both processes are started by PM2 (ecosystem.config.cjs) as telegram-agent-bridge-bot and telegram-agent-bridge-worker. Long polling means no public HTTPS endpoint is required for Telegram.

End-to-end pipeline

The literal path a single /task request takes, including the idempotency check that protects against Telegram's at-least-once delivery and the guardrail that stops a job before anything is pushed.

flowchart TD
    A["/task <description>\nin the allowed chat"] --> B{"Already have a job\nfor this chat+message?"}
    B -- "yes (redelivery)" --> Z["Ignore — no duplicate job"]
    B -- no --> C["Open a Telegram topic for the job\nInsert row, status = pending"]
    C --> D["Worker poll loop\natomically claims oldest pending job"]
    D --> E["Clone target repo at base branch\n(shallow, depth 50)"]
    E --> F["Create branch\nagent/<slug-of-task>-<job id>"]
    F --> G["Claude Agent SDK query()\nsystem prompt + per-job task prompt\nRead / Edit / Write / Glob / Grep + guarded Bash"]
    G --> H{"Agent succeeded\nAND changed files?"}
    H -- no --> I["Mark job failed\nreply ❌ in Telegram"]
    H -- yes --> J["git add -A && git commit"]
    J --> K["git push origin <branch>"]
    K --> L["Open DRAFT pull request\nvia GitHub API"]
    L --> M["Mark job completed\nreply ✅ + PR link in Telegram"]
    I --> N["Delete the local clone"]
    M --> N

Claude's entire contribution is the single "Agent" box. Everything before and after it — cloning, branching, committing, pushing, opening the PR — is plain deterministic TypeScript.

01
src/telegram/bot.ts

Intake & idempotency

Only TELEGRAM_ALLOWED_CHAT_ID can create jobs, and only via the explicit /task command — no message is ever treated as a task implicitly. Telegram long-polling delivers updates at-least-once, so before inserting anything the bot checks for an existing job with the same (chat_id, message_id); a unique index on that pair makes the insert itself idempotent as a second line of defense against a race. If the message replied to another one, that message's text is captured as contextNote.

02
src/worker/poll.ts · src/db/jobs.ts

Queue & claim

A worker loop polls the database every JOB_POLL_INTERVAL_MS. Claiming a job is one atomic UPDATE jobs SET status='running' … WHERE status='pending', so it's safe even if more than one worker process were ever run.

03
src/github/repo.ts

Workspace setup

The target repo is cloned fresh into a scratch directory at the job's base branch, then a new branch is checked out: agent/<slugified-task>-<job id>.

04
src/claude/session.ts · src/claude/prompt.ts · src/claude/security.ts

Agent run — this is where Claude writes code

The Claude Agent SDK's query() runs against the cloned working directory with a system prompt and a per-job task prompt (full text in Prompt flow). Every Bash call is checked against a denylist before it runs (see Permissions).

05
src/worker/pipeline.ts

Guardrail check

Two conditions fail the job before anything is pushed: the agent run reporting is_error, or the agent finishing with a clean working tree (no files changed). Either way, nothing gets committed.

06
src/github/repo.ts

Commit & push

git add -A plus a commit message naming the job number, requester, and Telegram origin — then git push -u origin <branch>.

07
src/github/pr.ts

Open the pull request

octokit.pulls.create with draft: true. Title is [agent] <task, truncated to 72 chars>; the body quotes the original task, names the requester, links back to the Telegram thread, and includes the agent's own closing summary.

08
src/worker/pipeline.ts

Notify & clean up

The job row is marked completed with the PR URL, a ✅ reply with the link goes into the Telegram topic, and the local clone directory is deleted — win or lose, cleanup always runs in a finally block.

Session settings that shape the run
  • cwd — the freshly cloned repo directory, so file paths in tool calls are always relative to that checkout.
  • permissionMode: "acceptEdits" — file edits proceed without a human approving each one (this runs unattended).
  • maxTurns: 40 (default, overridable per call) — a hard ceiling on back-and-forth turns.
  • env — the worker's environment plus ANTHROPIC_API_KEY, so the session can authenticate.

Commands

Three distinct command surfaces: what a person types in Telegram, what the agent is allowed to run inside the repo, and what an operator runs on the server.

Telegram bot commands (src/telegram/bot.ts — only in TELEGRAM_ALLOWED_CHAT_ID)

CommandWhat it does
/task <description>Queues a new job. Creates a dedicated Telegram topic for it (when the chat supports forum topics), inserts a pending row, and acknowledges with the job id. Deduplicated against message redelivery.
/statusLists every job currently pending or running, with counts of each and a truncated task description per job.
/cancel <job id>Cancels a job only while it is still pending (marks it failed with reason "Cancelled by user"). A job already running can't be interrupted mid-flight — it finishes or fails on its own.
/helpPrints the command list above.

What the agent is allowed to run

Inside a job, Claude operates under a fixed tool allowlist plus a Bash-specific denylist — not a sandbox, but a real check where otherwise none exists.

ToolAccessNotes
Read / Glob / GrepallowedUnrestricted read access inside the cloned repo.
Edit / WriteallowedFile edits apply immediately (permissionMode: "acceptEdits") — no per-edit confirmation, since the session is unattended.
BashguardedNot in the static allowlist — every invocation is routed through canUseTool and checked against the denylist below. Anything not matched is allowed, so this is a denylist, not a sandbox.
git commit / push / PRnever availableNo tool exposes these to the model at all; they're performed by pipeline.ts after the session ends.

A matched command is denied with an explanation returned to the model instead of run; the agent is told to explain in its final summary if the task genuinely needed it, rather than retry around the block.

Why the agent never touches git or GitHub directly

The system prompt and task prompt both tell Claude the same thing; the tool allowlist backs it up (no push/PR-creation tool exists to call); and the Bash denylist explicitly blocks git push/git config/git remote as a third, independent layer. The actual commit, push, and PR creation happen afterward in pipeline.ts, driven by the requester's task text and the agent's own summary — never by anything the model executed.

Job lifecycle & data model

Every job is one row in a SQLite jobs table. Status only ever moves forward, except for the crash-recovery requeue.

stateDiagram-v2
    [*] --> pending: /task received (deduped by chat+message id)
    pending --> running: worker atomically claims it
    pending --> failed: /cancel (only while still pending)
    running --> completed: agent made changes, commit+push+PR succeeded
    running --> failed: agent error, no changes, or push/PR failure
    running --> pending: worker crashed mid-job (stuck > STUCK_JOB_TIMEOUT_MS), attempts < 3
    running --> failed: stuck & requeued 3 times already
    completed --> [*]
    failed --> [*]

The crash-recovery check runs once at worker startup (Jobs.resetStuck): any job still running past the timeout is assumed orphaned by a dead worker process.

ColumnPurpose
task_descriptionThe text after /task — becomes the prompt body and PR title/body.
context_noteText of the message /task replied to, if any.
requesting_user_id / requesting_usernameWho asked — recorded in the commit message and PR body.
chat_id / message_id / message_thread_idWhere to reply; also the uniqueness key that prevents duplicate jobs from redelivered updates.
target_repo / target_base_branchWhich repo and base branch to clone (currently always GITHUB_REPO / GITHUB_BASE_BRANCH).
statuspending | running | completed | failed, enforced by a CHECK constraint.
branch_name / pr_url / error_messageFilled in as the job progresses.
